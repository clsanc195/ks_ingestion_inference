A knowledge graph AI proposes
and humans admit.

kgi ingests heterogeneous documents, extracts candidate knowledge with LLMs, and maintains a canonical graph under one invariant: nothing enters except an approved commit. Every fact traces to its source, its extraction run, and the human decision that admitted it.

01 · Problem statement

LLMs can read your documents. That doesn't make the result trustworthy.

Organizations hold their knowledge in heterogeneous documents — PDFs, Word files, markdown, process diagrams, transcripts. LLMs are now good enough to read all of them and propose structured facts. But naïvely piping extraction output into a database produces a knowledge base nobody can rely on, for five compounding reasons:

  • Extraction is noisy. Models hallucinate relations, invert directions, and phrase the same fact five different ways across documents.
  • Entities fragment. "Acme Corp", "Acme Corporation" and "the company" become three nodes; worse, two similarly-named but distinct things — a product and its successor, a parent and its subsidiary — get merged. Over-merging is the costlier failure: it's nearly invisible after the fact.
  • Knowledge changes, stores don't. A CEO is replaced; an HQ moves. Append-only graphs accumulate contradictions; destructive updates erase history.
  • No provenance, no trust. In any serious setting — finance, compliance, operations — a fact that can't answer "where did this come from and who approved it?" is a liability, not an asset.
  • Answers inherit all of it. Retrieval over a corrupted store confidently serves duplicates, stale facts, and inventions.

The task, precisely stated: build a system that extracts knowledge from any document, correlates it against everything already known — recognizing when a new fact is the same, reinforcing, extending, or contradicting — and adjusts the graph accordingly, with a human quality gate and full auditability, at a review burden small enough to be sustainable.

02 · Proposed solution

A pull-request workflow for knowledge

Core invariant

The canonical graph is only ever mutated by an approved commit. All inference lands in a staging layer; the human review gate is the promotion boundary. Everything else in the architecture exists to serve this rule.

Extraction never writes to the graph. It compiles into a patch — a dependency-ordered set of typed operations (create_node, merge_into, assert_edge, invalidate_edge…) diffed against current canonical. Ops are confidence-scored and routed: high-confidence auto-approves, everything ambiguous queues for a human, and the run parks durably at the gate — for days if needed. On approval, an idempotent commit engine applies the patch and writes provenance in the same transaction.

The five design decisions that shape everything else

DecisionChoiceConsequence
Domain scopeOpen-domainNo fixed ontology; a thin upper seed plus induced types, each type itself human-gated.
ContradictionsTieredValue-changed-over-time auto-reconciles bi-temporally; incompatible same-time claims always escalate to a human.

03 · Research foundations

What the literature contributed — and where this design departs

Each layer borrows its strongest available idea from published work. The synthesis — treating the HITL gate as a promotion boundary with patch semantics, rebase checks, and commit-time provenance — is the part not found in any single system below.

Two departures worth naming. Most published pipelines write extraction output directly to the store and treat cleanup as post-processing; here nothing is written until reviewed, which converts quality control from batch repair into a gate. And cosine matching is used only as a tier: measurement showed true aliases score ~0.99 while distinct siblings score ~0.87, so the ambiguous band escalates to an LLM judge prompted to refuse uncertain merges.

04 · Components

Eleven components, one module each

The package mirrors the architecture: every stage is an importable module with one responsibility. All LLM usage funnels through a single traced entry point (kgi/llm.py), and only one component is allowed to write to canonical.

Ingestion

kgi/ingestion

Pluggable per-format parsers → normalized blocks. BPMN parses as ground truth (it is already a typed graph) and skips LLM extraction entirely. Content-hash registration makes re-ingestion a no-op.

Decomposition

kgi/decomposition

Blocks → extraction units; headings travel as context, not content. v1 is paragraph-per-unit; the atomic-fact atomizer swaps in behind the same interface.

Extraction

kgi/extraction

One structured LLM call per unit → candidate entities and relations, each with a verbatim evidence quote and confidence. Guided by canonical's live vocabulary so repeat documents reuse terms.

Schema manager

kgi/schema

Thin upper ontology (Agent, Event, Artifact…) plus induced types. Never-seen types force human review regardless of confidence.

Resolution cascade

kgi/resolution

Rules (exact name) → embedding ANN with calibrated accept/reject bands → LLM judge for the ambiguous middle. Non-trivial matches become reviewable merge_into ops with SAME_AS provenance.

Conflict engine

kgi/conflict

Detects colliding facts on either shared endpoint (HQ moved; CEO replaced). An LLM adjudicator classifies: compatible / temporal supersession (auto bi-temporal ops) / semantic conflict (forced review).

Confidence & routing

kgi/confidence · kgi/routing

Weighted blend of extraction confidence, source support, resolution score, and schema validation → auto-approve / review / auto-reject, with force-review overrides.

Review gate

kgi/pipeline (interrupt)

The run parks durably (Postgres checkpoint) and survives restarts. Decisions — accept, reject-with-note, defer — arrive from terminal or browser and are recorded as provenance.

Commit engine

kgi/commit

The only writer to canonical. Idempotency ledger, rebase-checked preconditions, dependency ordering (an edge whose endpoint was rejected blocks), provenance in the same transaction.

Retrieval

kgi/retrieval

Vector-anchored entity lookup → temporal-filtered graph expansion → grounded answers that must cite fact ids or refuse. --as-of reconstructs any past state.

Viewer

kgi/viewer

FastAPI + SVG canvas: the graph, per-node provenance panels, search/ask with citation highlighting, and an actionable review queue. Approvals resume the parked run.

Command surface: kgi ingest · pending · review · search · ask · serve

05 · Infrastructure

One system of record, three helpers

The stores are deliberately unequal. Neo4j holds everything that is the system; the others are a rebuildable similarity index, a pause button, and a telescope. Knowing which is which is most of operating it.

StoreRoleContentsIf lost
Neo4jSystem of record Canonical entities and bi-temporal facts; SAME_AS aliases; the AppliedOp commit ledger; document hashes; review decisions; staged patches (as JSON — never as graph structure) Total loss. Everything else derives from it.
QdrantSimilarity index 384-dim embeddings of entity names and predicate phrases only — computed locally (bge-small via fastembed, no API), written only at commit time. No document text, no chunks, no facts. Zero knowledge lost; re-embed from Neo4j in minutes.
PostgresDurable execution LangGraph checkpoints — the saved state of runs parked at the review gate Parked runs lost; staged patches survive in Neo4j.
LangfuseObservability Traces: one per command, node spans, every LLM generation with prompt, parsed output, and token usage Trace history only; no effect on the system.
Anthropic APIThe four LLM roles Extractor, resolution judge, conflict adjudicator, answer composer — one configured model, one traced call path Ingestion and ask pause; the graph and queries keep working.

Who touches which store, when

Not a RAG vector store

Nothing embeds document chunks. Knowledge lives as explicit, reviewed graph facts; embeddings exist only to recognize that two short strings name the same thing. Staged candidates are never indexed — an unreviewed fact cannot influence how the next document resolves.

06 · Deployment & runtime topology

Two ephemeral processes, one server, four containers

Lifecycles that matter operationally

  • CLI commands are fresh processes — they pick up config changes immediately. The viewer is not: restart it after code or .env changes (the recurring dev gotcha).
  • A parked run outlives every process. Ingest exits after staging; days later, review resumes it from the Postgres checkpoint — CLI and browser both resume the same run.
  • All state survives restarts via named Docker volumes. The integration test suite wipes the Neo4j instance it points at — a dev-only hazard, flagged for isolation work.
  • Path to production: containerize the app, move the gate's durability to managed Postgres, and treat Temporal as the orchestration upgrade if runs become mission-critical.
07 · Lifecycle

The life of one document, drop-off to answer

Follow a single document — say, an updated company profile arriving into a graph that already holds an earlier version of the story — through every vertical. Steps 01–06 are inference and cost tokens; the amber steps are the gate; everything after it is deterministic bookkeeping.

  1. Register & fingerprint

    The file's bytes are hashed; the hash is the document's identity. If an identical document was already committed, the run ends here as an explicit no-op — idempotency starts before any parsing. Structured formats (BPMN) short-circuit differently: they are already typed graphs, so their structure enters as ground-truth candidates that never need an LLM.

  2. Normalize & decompose

    The modality parser emits uniform blocks; headings and layout become context attached to each block rather than content. Blocks become extraction units — the bite-sized pieces the extractor reads one at a time, each carrying its lineage (document, block, position) forward.

  3. Extract candidates

    One structured LLM call per unit returns candidate entities and relations — each with a verbatim evidence quote and a confidence. The prompt carries the graph's current type and predicate vocabulary, so a repeat concept arrives under the name canonical already uses instead of a fresh paraphrase. Candidates are proposals in memory; nothing has been stored anywhere.

  4. Resolve identities

    First within the batch: paragraphs re-mentioning the same name collapse into one candidate, evidence accumulating. Then against canonical, cheapest tier first: exact name → reuse the existing node; embedding similarity above the accept band → a reviewable merge_into with SAME_AS provenance; the ambiguous middle → an LLM judge instructed that a false merge is worse than a duplicate; no match → create_node. Predicates normalize the same way, so "is led by" and "has CEO" don't fork the vocabulary.

  5. Correlate against what the graph believes

    Each surviving relation is compared with canonical's current edges. Same fact → a reinforce (support count grows). Novel fact → an assert. A collision — same predicate, one shared endpoint, the other end different (the headquarters moved; the role changed hands) — goes to an adjudicator: compatible facts coexist; temporal supersession pairs the new assertion with an invalidate_edge closing the old fact's validity window; a semantic conflict — incompatible claims with no evidence of change — is marked for mandatory human judgment. Every op records preconditions: a snapshot of the canonical state it was diffed against.

  6. Score & route

    Each op earns a blended confidence — extraction certainty, source support, resolution score, schema validation — and policy routes it: auto-approve above the high bar, auto-reject below the floor, human review between. Some ops ignore the score entirely: never-seen types, semantic conflicts, and high-blast-radius merges always face a human.

  7. Stage & park

    The full patch is persisted to staging — as a document, deliberately not as graph structure, so nothing downstream can query half-approved knowledge. The run checkpoints and the process exits. Canonical is untouched; the queue shows one pending patch; days may pass.

  8. Human adjudication

    The curator works the queue — terminal or browser — op by op: accept, edit, reject with a note, or defer. Each decision is recorded as provenance with reviewer identity and timestamp; deferred ops simply stay pending. Submitting resumes the parked run exactly where it stopped.

  9. Commit, or refuse to

    Approved ops apply in dependency order, one transaction each: the ledger is checked (already applied → skip, which is what makes crash-and-retry safe), then preconditions are re-verified against current canonical — if the graph moved since the diff, the op re-queues instead of applying blind. An op whose dependency was rejected blocks. What survives is written together with its provenance; only then are the new entity names and predicates indexed for the next document's resolution, and the document hash marked done.

  10. Serve

    The knowledge is now queryable three ways that matter: current — "who leads the company?" answers with the new fact, cited to its source and approval; historical — the same question --as-of an earlier date answers with the superseded fact, because closing a validity window is not deletion; and honestly not at all — a question the reviewed facts can't support gets an explicit refusal, never a guess.

One document in, three kinds of truthful answers out — and at every step between, a place where a wrong proposal could be caught, priced, or reversed.

08 · Trust & audit model

Every fact answers: where from, who approved, when true

The audit chain is graph structure, not log files. For any edge, one traversal yields the complete story: 

(fact edge) ⟵ AppliedOp {patch, extraction run, committed-at}
                 ⟵ Document {source file, content hash}
                 ⟵ ReviewDecision {reviewer, action, note, timestamp}
                 — or "auto-approved by policy", explicitly recorded
  • Bi-temporal honesty. Facts carry validity windows; contradiction closes a window rather than deleting. History stays queryable and answers cite the closed edge when asked about the past.
  • Reversible merges. Entity merges keep the source identity as an Alias —SAME_AS→ record with method and score — the one mistake that is hard to detect later (over-merging) stays undoable.
  • Rejected knowledge leaves a trace. Staged patches are never deleted; a rejected claim, its rationale, and the reviewer's note remain in the audit trail without ever having touched canonical.

When bad facts get in anyway — the remediation playbook

A pipeline bug that admits wrong facts is a data-quality incident, and the design supports the standard response: scope the blast radius from the ledger (facts are queryable by run, patch, and time), quarantine by flag rather than deletion, correct forward with remediation patches through the same gate, and reprocess affected documents against fixed code — re-extraction diffs naturally against current canonical. Never hand-edit the store: an unledgered mutation is the one thing the invariant cannot forgive.

09 · Observability

One trace per command, one call path for every LLM decision

All four LLM roles go through a single instrumented entry point, so Langfuse receives every prompt, parsed output, and token count the system produces. Pipeline runs open a named root span; LangGraph node spans and the generations made inside them nest beneath it. 

kgi-ingest <document>                        ⟵ root span (outcome recorded)
 └─ LangGraph
     ├─ parse · decompose                     ⟵ node spans
     ├─ extract
     │   └─ extract-unit ×4                   ⟵ generations (tokens, cost)
     ├─ resolve
     │   ├─ resolution-judge ×N               ⟵ "same entity?" verdicts
     │   └─ conflict-adjudicator ×N           ⟵ supersession reasoning
     └─ score_route · stage

kgi-review patch_…  (same session id)         ⟵ the approval, days later
kgi-ask "…"                                   ⟵ retrieval + grounded-answer
  • Session = document journey. The run's thread id becomes the Langfuse session, so an ingest and its later review resume group together.
  • Judge decisions are inspectable. The exact adjudicator prompt that produced a supersession op in the review queue is one click away.
  • Cost is attributable per document, per stage, per role — extraction dominates, judges are the rare expensive tail, as designed.
  • Fail-open by construction. Tracing activates only when keys are present and every helper no-ops on error; observability can never block ingestion.
