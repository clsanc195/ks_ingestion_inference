01 · Overview

kgi — governed knowledge-graph ingestion

kgi turns heterogeneous documents (markdown, PDF, DOCX, BPMN) into a canonical knowledge graph. LLMs propose facts; humans admit them. The system exists because raw LLM extraction is unusable as a system of record: entities fragment or over-merge, facts contradict as the world changes, and nothing is attributable.

Invariant

The canonical graph is mutated only by approved commits. All inference lands in staging; the human review gate is the promotion boundary. Every fact is traceable to its source document, extraction run, and admitting decision.

Mechanically, it is a pull-request workflow for knowledge: extraction compiles into a patch — a dependency-ordered set of typed ops (create_node, merge_into, assert_edge, invalidate_edge) diffed against canonical. Ops are confidence-routed (auto-approve / review / auto-reject), the run parks durably at the gate, and an idempotent commit engine applies approved ops with provenance in the same transaction. Facts are bi-temporal[3]: contradiction closes a validity window, never deletes.

02 · Architecture

How the components connect

One durable pipeline per document. Stages call the shared LLM service and read the stores; only the commit stage writes canonical. Both interfaces drive the same parked run — the gate is a pipeline state, not a UI feature.

  • Single LLM chokepoint. Extract, the resolution judge, the conflict adjudicator, and the query composer all call one traced entry point; no stage owns a private client.
  • Single write path. Stages before the gate read stores and write only staging; commit alone writes canonical, and the vector index is written after commit succeeds.
  • The gate is durable state. Park/resume goes through Postgres checkpoints, which is why the CLI and the viewer can adjudicate the same run.

Note this is not a RAG vector store: no document chunks are embedded. Knowledge lives as reviewed graph facts; vectors exist only to match short strings (names, predicate phrases), and staged candidates are never indexed.

05 · Runtime topology

Processes, containers, ports

  • CLI processes are fresh per command and pick up .env immediately; the viewer must be restarted after code/config changes.
  • A parked run outlives every process; CLI and browser resume the same checkpoint.
  • Production path: containerize the app, managed Postgres, Temporal if runs become mission-critical.
06 · Ingestion lifecycle

One document, register to commit

Running example throughout: a two-sentence profile — "Acme Corp is headquartered in Basel. Elena Vogel has been CEO of Acme Corp since 2020." — arriving into a graph that already knows Acme Corporation, headquartered in Zurich.

  1. Register. SHA-256 of the bytes is the document's identity; a hash already committed ends the run as a no-op. Structured formats (BPMN) enter as ground-truth candidates without extraction.

    sha256(profile.md) → doc_a1b2c3… Neo4j :Document{hash}? → not found → continue (found → "duplicate — nothing to do", run ends)

  2. Normalize & decompose. Parser emits blocks; headings become per-unit context; each unit keeps lineage (document, block).

    unit 1 · context: heading "Acme profile" "Acme Corp is headquartered in Basel. Elena Vogel has been CEO of Acme Corp since 2020."

  3. Extract. One structured LLM call per unit → candidate entities and relations with verbatim evidence quotes and confidence, guided by canonical's current type/predicate vocabulary.

    entities: Acme Corp (Agent .92) · Basel (Place .88) Elena Vogel (Agent .95) relation: (Acme Corp) —headquartered in→ (Basel) quote: "Acme Corp is headquartered in Basel" relation: (Elena Vogel) —is CEO of→ (Acme Corp) · from 2020

  4. Resolve. Intra-batch dedup, then the cascade per entity: exact name → reuse; embedding ≥0.93 → merge_into; 0.70–0.93 → LLM judge; else create_node. Predicates normalize against known phrases (≥0.85).

    "Acme Corp" exact? no → Qdrant: 0.99 vs "Acme Corporation" → merge_into "Basel" exact? no → best 0.41 → create_node "Elena Vogel" exact match → reuse node (0.70–0.93 band → LLM judge decides)

  5. Correlate. Per relation vs current edges: duplicate → reinforce; novel → assert; shared-endpoint collision → adjudicate (compatible · temporal supersession · semantic conflict). Every op snapshots preconditions.

    Neo4j holds (Acme)—headquartered in→(Zurich), current new Basel edge shares subject + predicate → adjudicate quote has no move, no dates → semantic_conflict CEO edge: no existing collision → plain assert

  6. Score & route. Blended confidence → auto-approve ≥0.92, auto-reject <0.30, else review. New types, semantic conflicts, and high-degree merges force review regardless of score.

    op1 merge_into Acme Corp→… .82 → review op2 create_node Basel .71 → review op3 assert_edge hq→Basel ⚠ — → review forced op4 assert_edge CEO from 2020 .94 → auto-approve

  7. Stage & park. Patch persisted to staging (as a document, not graph structure); run checkpoints; process exits. Canonical untouched.

    :Patch{id: patch_7f3e21, json, thread_id} → Neo4j staging run checkpoint → Postgres · process exits canonical graph: byte-for-byte unchanged

  8. Review. Curator accepts / edits / rejects-with-note / defers per op; each decision recorded with identity and timestamp; submit resumes the run.

    op1 ✓ accept · op2 ✓ accept op3 ✗ reject — note: "Zurich is correct" each click → :ReviewDecision{reviewer, action, at} submit → parked run resumes from checkpoint

  9. Commit. Approved ops in dependency order, one transaction each: ledger check (idempotent retry), precondition re-verify (stale → requeue), dependency blocking, provenance atomic with the fact. Then vectors are indexed and the doc hash marked done.

    apply op1, op2, op4 · per op: fact + :AppliedOp ledger op3: rejected — never becomes graph structure then Qdrant += "Basel" · :Document{hash} marked done re-ingesting profile.md tomorrow → stops at step 01
07 · Query path

Anchor, expand, compose

  • Temporal semantics. Default view keeps edges with open validity windows; --as-of DATE keeps edges whose window covers the date — the same graph answers current and historical questions differently, both cited.
  • Provenance rides along. Each retrieved fact carries its source documents via the commit ledger; citations resolve to files and decisions.
  • Honest failure. If retrieved facts can't support the question, the composer must say so — cited-id validation drops any hallucinated reference.
08 · Design record

Decisions and the audit model

DecisionChoiceConsequence
Domain scopeOpen-domainNo fixed ontology; thin upper seed + gated induced types[5].
ContradictionsTieredChange-over-time auto-reconciles bi-temporally[3]; incompatible same-time claims always escalate.
ReversibilityReversible merges; forward-fix the restMerges keep SAME_AS provenance; other errors corrected by new reviewed patches, never edits.
Review stalenessNo expiry; rebase at commitPreconditions re-verified at commit; stale diffs requeue instead of applying blind.
CurationSingle curator (v1)Reviewer identity recorded from day one; multi-reviewer needs no migration.

Audit chain (graph structure, not logs)

(fact edge) ⟵ AppliedOp {patch · extraction run · committed-at}
              ⟵ Document {source file · content hash}
              ⟵ ReviewDecision {reviewer · action · note · timestamp}
                 — or "auto-approved by policy", explicitly recorded

Remediation for bad commits follows data-quality incident practice: scope via the ledger, quarantine by flag, correct forward through the same gate, reprocess affected documents against fixed code. Hand-editing the store is the one forbidden move.

10 · References

Publications and systems informing the design

  1. Edge et al., "From Local to Global: A GraphRAG Approach" (2024) — LLM-built graphs as retrieval substrate; local/global search framing. Adopted: local search. Deferred: community summaries.
  2. Lairgi et al., "iText2KG: Incremental Knowledge Graphs Construction" (WISE 2024, arXiv:2409.03284) — incremental construction, embedding-cosine entity resolution. Adopted as cascade tier 2, with thresholds recalibrated on measured collision pairs (aliases ≈0.99 vs distinct siblings ≈0.87).
  3. Rasmussen et al., "Zep: Graphiti" (2025) — bi-temporal knowledge-graph memory: validity windows instead of deletion. Adopted for all facts; basis of as-of queries.
  4. "ATOM: Atomic-fact decomposition" (arXiv:2510.22590) — proposition-level units for extraction precision. Designed upgrade path behind the decomposition seam.
  5. Bai et al., "AutoSchemaKG" (arXiv:2505.23628) — dynamic schema induction. Adopted with governance added: induced types are human-gated under a thin upper ontology.
  6. SCICERO / HITL-validation line (ScienceDirect, 2025) — source-support counts as confidence signal; human validation loops. Adopted in the scorer and the gate design.
  7. "Less is More: Denoising Knowledge Graphs for RAG" (arXiv:2510.14271) — entity resolution as retrieval quality control. Justifies the LLM judge tier and the conservative no-merge default.
  8. Guo et al., "LightRAG" (2024) and "LLM-empowered KG construction: a survey" (arXiv:2510.20345) — design-space and cost-tier mapping used in the layer-by-layer option analysis.
  9. Neo4j LLM Knowledge Graph Builder — reference implementation of extraction→Neo4j plumbing; baseline the staging/commit split improves on.

The synthesis not found in any single source: the HITL gate as a promotion boundary with patch semantics, rebase-checked commits, and transaction-atomic provenance.
