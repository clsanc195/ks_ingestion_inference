01 · Overview

kgi — a knowledge graph written by LLMs, approved by humans

kgi reads documents (markdown, PDF, DOCX, BPMN), uses an LLM to extract facts, and stores them in a graph database — but only after a human approves each change. The approval step exists because raw LLM extraction can't be trusted as a source of truth: it produces duplicate entities, wrong merges, contradictions as the world changes, and no record of where a fact came from.

The one rule

Only approved commits write to the main graph. Everything the LLM produces goes to staging first; human review sits between staging and the graph. Every stored fact links back to its source document, its extraction run, and the approval decision.

Mechanically it works like a pull request. Extraction output is compiled into a patch: a list of typed ops (create_node, merge_into, assert_edge, invalidate_edge) diffed against the current graph. Each op gets a confidence score — high auto-approves, low auto-rejects, the middle goes to a review queue. The run pauses at review (for days if needed); on approval an idempotent commit applies the ops and writes the audit records in the same transaction. Facts carry valid_from/valid_to dates[3]: a contradicted fact gets an end date instead of being deleted, so history stays queryable.

02 · Architecture

How the components connect

One pipeline run per document. Stages call one shared LLM client and read the databases; only the commit stage writes the main graph. The CLI and the web UI resume the same paused run — review is a pipeline state, not a UI feature.

  • One LLM client. Extraction, both LLM-as-judge roles (entity dedup, conflict decisions), and query answering call one traced function; no stage owns a private client.
  • One write path. Stages before review only read; commit alone writes the graph, and vectors are indexed only after commit succeeds.
  • Review survives restarts. Pause/resume goes through Postgres checkpoints, so the process can exit and CLI or browser can pick the run up days later.

The Neo4j data model, concretely

(:Canonical {id, name, entity_type, description, confidence, …})  — an entity + what it IS
(a:Canonical)-[:REL {id, predicate, valid_from, valid_to,
                     support, quotes: [..], confidence,
                     invalidation_reason}]->(b:Canonical)          — a fact + every source's wording
(:Alias {match_method, match_score})-[:SAME_AS]->(:Canonical)      — an undoable merge
(:AppliedOp {op_id, patch_id, doc_id, at})-[:WROTE]->(node)        — commit ledger
(:Patch {id, status, json, thread_id})                             — staged proposal
(:Document {content_hash, source_uri})                             — ingest dedup
(:ReviewDecision {op_id, reviewer_id, action, note, decided_at})   — the approval

FULLTEXT INDEX entity_text ON (name, description)                  — the BM25 door,
FULLTEXT INDEX fact_text   ON (predicate, quote, quotes)             auto-maintained

Predicates are edge properties, not Neo4j relationship types — the LLM invents predicate names at runtime, and fixed queries over one relationship type handle any vocabulary. "Current facts" = valid_to IS NULL.

Still not a RAG chunk store: no document text is embedded wholesale. What is embedded are three kinds of short, reviewed strings — entity name + description, predicate phrases, and one-line fact renderings with their quotes. Every vector is a derived copy of graph content (scripts/reindex_vectors.py rebuilds all three collections from Neo4j), and staged candidates are never indexed.

Runtime topology

  • CLI processes are fresh per command and pick up .env immediately; the viewer must be restarted after code/config changes.
  • A parked run outlives every process; CLI and browser resume the same checkpoint.
  • Production path: containerize the app, managed Postgres, Temporal if runs become mission-critical.

The audit trail (graph structure, not log files)

(fact edge) ⟵ AppliedOp {patch · extraction run · committed-at}
              ⟵ Document {source file · content hash}
              ⟵ ReviewDecision {reviewer · action · note · timestamp}
                 — or "auto-approved by policy", explicitly recorded

If a bug ever lets bad facts in: find them via the commit ledger, flag them, fix forward with new reviewed patches, and re-run the affected documents on fixed code. Never hand-edit the database — an unaudited change breaks the one guarantee everything else relies on.

Ingestion · overview

One document, nine steps, one paused run

The next nine pages walk a single document through the pipeline, one step per page — with the real system prompts where an LLM is called, the real queries where a database is consulted, and the real code where an algorithm matters. The LLM appears exactly three times (steps 3, 4, 5); a human exactly once (step 8); the main graph is written exactly once (step 9).

Running example

You run kgi ingest profile.md on a two-sentence file — "Acme Corp is headquartered in Basel. Elena Vogel has been CEO of Acme Corp since 2020." — arriving into a graph that already knows Acme Corporation, headquartered in Zurich. Every step page shows this document's actual data.

Ingestion · step 1 of 9

Register

The file's raw bytes are hashed with SHA-256. That hash is the document's identity from now on — not the filename, not the path: the content. Then one Neo4j query asks whether a :Document node with this hash already exists. Found → this exact content was already ingested and committed; print duplicate — nothing to do and the run ends, before any parsing or LLM cost. Not found (our case) → continue.

sha256(profile.md) → doc_a1b2c3… Neo4j :Document{hash}? → not found → continue (found → "duplicate — nothing to do", run ends)

Ingestion · step 2 of 9

Decompose

Two small transformations, zero AI, zero database writes. The markdown parser splits the file on blank lines; headings don't become content — they update a running "where am I" stack. Then each content block becomes an extraction unit: the piece the LLM will read in step 3, carrying its text, its heading context, and its lineage (which document, which block).

block 0: heading "# Acme profile" → pushes onto the heading stack block 1: paragraph "Acme Corp is headquartered in Basel. Elena Vogel has been CEO of Acme Corp since 2020." unit_id: doc_a1b2c3_b1_u0 ← lineage: doc + block context: {"headings": ["Acme profile"]}
CODEsrc/kgi/decomposition/atomizer.py:10 · decompose()

        unit_id=f"{block.block_id}_u0",

  • The cut is by paragraph, not sentence — both sentences travel together, so "Elena Vogel has been CEO" keeps the sentence naming Acme right next to it.
  • Unit count = LLM cost. Our document → 1 unit. A ten-paragraph report → 10 units → 10 LLM calls in step 3.
  • unit_id is the future evidence anchor — a fact stored months from now points back through it to the exact block of the exact document.

Sentence-level "atomic fact" splitting is the planned upgrade behind this same function. BPMN files skip this step entirely — they are already graphs.

Ingestion · step 3 of 9

Extract LLM CALL

Our unit goes to Claude — one call per unit, which is where ingestion spends nearly all of its money. The system prompt demands verbatim supporting quotes and forbids anything the text doesn't explicitly say; it also lists the type and predicate names already in the graph, so the model reuses "headquartered in" instead of coining "based in". Output is pinned to a Pydantic schema via Instructor — malformed responses are automatically re-asked; there is no free-text parsing anywhere.

Ingestion · step 4 of 9

Dedup entities LLM-AS-JUDGE

For each candidate: "do I already know this thing?" Wrong in one direction → duplicates; wrong in the other → two different things glued together, which is worse because it's nearly invisible afterwards. So: a cascade of three tiers, cheap checks first, expensive judgment only when needed — after first collapsing re-mentions within the document itself.

TierCheckCostSettles
tier 1Exact name match in Neo4j (case-insensitive)Free — one indexed lookupIdentical spellings
tier 2Embed name + description locally, cosine-search Qdrant. Same if ≥ 0.90, new if < 0.60Cheap — milliseconds, no APIObvious variants and obvious strangers
tier 3LLM-as-judge (sees descriptions), for scores between 0.60 and 0.90Expensive — one Claude callThe genuinely ambiguous few percent

  • Only approved knowledge is searchable. Candidates still waiting in someone's review queue are invisible to matching here.

Predicates take the cheap path — deliberately

The cascade above is for entities only. Predicates ("headquartered in", "is CEO of") get one check and no ceremony:

EntitiesPredicates
What they areNodes with identityStrings stored as a property on edges
Checkexact → vector → LLM-as-judgeOne vector search against known predicate phrases
On a matchA merge_into op — through the gates, undoable via SAME_AS≥0.85 similar → silently rewritten to the known phrasing ("is chief executive officer of" → "is CEO of"). No op, no review, no undo record.
On no matchA create_node op → the gatesThe new phrasing is simply used, and indexed at commit
Cost of a wrong callTwo things glued together — nearly invisible laterTwo phrasings coexist — ugly but harmless and visible

The asymmetry is intentional: a wrong entity merge corrupts identity, so entities earn the expensive machinery; a wrong predicate mapping just splits vocabulary. Note one looseness that scale will eventually expose: a never-seen entity type forces human review, but a never-seen predicate sails through inside its fact's op.

Ingestion · step 5 of 9

Detect conflicts LLM-AS-JUDGE

Each relation is compared against what the graph currently believes. The CEO fact finds nothing on its endpoints → plain assert_edge. (An exact duplicate would instead reinforce: support count +1 and the new source's verbatim quote appended to the edge's quotes list.) The headquarters fact trips the interesting wire: a current fact shares an endpoint and predicate but disagrees on the other end.

new: (Acme Corporation) —headquartered in→ (Basel) existing: (Acme Corporation) —headquartered in→ (Zurich) valid_to: NULL same subject + predicate ─────────── different object → collision

LLM-AS-JUDGEconflict verdict · src/kgi/conflict/engine.py
SYSTEM: You adjudicate potential contradictions in a knowledge graph.
An existing fact and a new fact share the same predicate and one
endpoint, but differ on the other endpoint. Classify the pair:
- compatible: both can be true at the same time (a company has many
  divisions; several co-founders).
- temporal_supersession: the new fact replaces the old one over time —
  the evidence clearly indicates a change (a successor taking a role,
  explicit dates, words like "replaced" / "until").
- semantic_conflict: the claims cannot both be true and there is no
  clear evidence of change over time.
Be conservative: if the evidence does not clearly indicate change over
time, answer semantic_conflict. A wrong supersession silently rewrites
history; an escalation only costs one human review.

Three verdicts, three destinies:

  • Both true → assert alongside; a company has many products.
  • Value changed over time → the patch automatically pairs the new assert with an invalidate_edge end-dating the old fact — history preserved, no human needed.
  • True contradiction — our case: a flat claim, no move language, no dates → the op is flagged and forced to human review regardless of its score.

Ingestion · step 6 of 9

Score & route

Each op gets a number and a destination. No AI here — arithmetic and thresholds. Plus overrides that ignore the score entirely: a never-seen entity type, a flagged contradiction, or a merge into a heavily-connected node always goes to review. High confidence doesn't buy past those.

op1 merge_into Acme Corp→Acme Corporation .82 → review op2 create_node Basel .71 → review op3 assert_edge HQ→Basel ⚠ contradiction — → review (forced) op4 assert_edge CEO, from 2020 .67 → review nothing clears the 0.92 bar on a cold graph — see Scoring & gates
  • Nothing here clears 0.92 — deliberately. A novel fact on an empty graph carries support 1 and a neutral "new" resolution signal, capping its blend near 0.70. Cold starts are skeptical by design; the full arithmetic, the gates, and the levers have their own section.
  • The weights are versioned guesses. Every reviewer accept/reject is stored as a labeled example — exactly the data that will calibrate them later.
  • All-auto patches skip the pause. If every op auto-approves, the run bypasses review entirely — the needs_review diamond in the LangGraph figure.
Ingestion · step 7 of 9

Stage & pause

Everything computed so far becomes durable, and then the program stops. The four ops — routes, scores, recorded assumptions, evidence — are serialized into one patch and saved to Neo4j as a JSON blob on a single node: deliberately not graph structure, so no query, no retrieval, no dedup search can ever treat half-approved knowledge as real. Staging and the main graph share a database, separated by shape.

Ingestion · step 9 of 9

Commit

The only code in the system allowed to write the main graph runs now — one transaction per op, three checks before each write: the ledger (already applied? skip — crash-and-retry can't double-write), the recorded assumptions (graph changed while you deliberated? requeue, don't apply blind), and dependencies (edge whose endpoint was rejected? blocked). Pass all three → the write and its audit record commit in the same transaction.

CODEsrc/kgi/commit/engine.py · the per-op transaction
def _tx(tx, routed=routed, op=op):
    if tx.run("MATCH (a:AppliedOp {op_id: $id}) RETURN a", id=op.op_id).single():
        return "committed"                        # ledger: already applied
    if not all(_check_precondition(tx, p) for p in op.preconditions):
        return "requeued"                         # graph moved → don't apply blind
    applier.apply(tx, op)                         # the write + :AppliedOp receipt
    return "committed"

04 · The patch system

The patch: everything downstream of extraction is one data structure

Resolution never writes anything. Its entire output — for one document, one run — is a patch: a list of typed operations diffed against the current graph, exactly like a pull request is a diff against the current code. The patch is what gets scored, what the human reviews, what the commit engine applies, and what the audit trail keeps forever. Understand the patch and you understand the system.

Ops form a dependency graph, not a list

Preconditions: the graph as it was, notarized

A patch can wait at the gate for weeks while other patches land. So every op records the assumptions it was diffed against, and the commit engine re-verifies them inside the write transaction. A failed check requeues the op — it never applies blind.

PreconditionCarried byGuards against
node_exists / edge_existsmerges, updates, invalidationsthe target vanished while the patch waited
edge_absentasserts between known nodessomeone committed the same fact first — requeue, don't duplicate
name_absentevery createthe classic race: document B resolved against an empty graph while document A was parked; by commit time A landed. The twin requeues into dedup instead of being created
prop_equalsdescription mergesthe description changed concurrently — requeue rather than clobber the other writer's merge

The op lifecycle

pending ──(reviewer accepts / auto-approve)──▶ approved ──▶ committed │ │ │ (reviewer rejects / auto-reject) ├─(precondition failed)──▶ requeued ▼ └─(dependency lost)──────▶ blocked rejected — kept forever in the patch JSON, with the reviewer's note defer = no decision: the op stays pending, commit holds it back, and the run parks at the gate again after committing what WAS decided

Commit: one transaction per op, three checks, deterministic ids

CODEsrc/kgi/commit/engine.py · the exact shape of every write
def _tx(tx, op):
    if ledger_has(tx, op.op_id):        # check 1 — :AppliedOp receipt exists?
        return "committed"              #   crash-and-retry can't double-write
    if not all(_check_precondition(tx, p) for p in op.preconditions):
        return "requeued"               # check 2 — the graph moved: re-diff, don't apply
    applier.apply(tx, op)               # the write + its :AppliedOp receipt,
    return "committed"                  #   SAME transaction — all or nothing
# check 3 happens in the walk order itself: ops apply topologically, and an op
# whose dependency failed is marked blocked before its transaction ever opens.

# ids are minted from content, not randomness — a retry converges:
canonical_id = f"can_{sha1(f'{patch_id}:{op_id}')[:16]}"
  • The patch is the audit trail. It is never deleted: rejected ops, reviewer notes, original confidences and preconditions stay in the JSON forever. An auditor reconstructs exactly what was proposed, decided, and why.
  • Patch status follows its ops. All settled → committed and the document hash is marked done. Anything requeued → the patch says so. Anything deferred → still pending, the run parks again, and the intake lock refuses to stage the same document twice meanwhile.

06 · Warm-graph ingestion

The second document is the interesting one

On an empty graph, ingestion is simple: everything is new, every op is a create or an assert. The design only starts working for its living once the graph already knows things — because then every candidate must be reconciled with prior knowledge, not just added. This page traces one paragraph arriving into a warm graph, resolution decision by resolution decision, down to the ops it produces.

Setup

The graph already knows: Acme Corporation ("Swiss industrial group"), Elena Vogel, the facts (Acme) —headquartered in→ (Zurich) and (Elena Vogel) —is CEO of→ (Acme). A new document arrives: "Acme Corp's chief executive Elena Vogel opened the company's new plant in Basel in March 2024. Acme Corp remains headquartered in Zurich."

Read the matrix's consequence: on a cold graph, auto-approve is mathematically unreachable — novel facts cap ≈0.70, and only triple-corroborated duplicates clear 0.92. That is deliberate skepticism, but one signal is genuinely mis-scored: when the best similarity hit is 0.41, "new" isn't uncertainty — it's positive evidence of novelty, and scoring it 0.5 conflates the two. The levers, cheapest first: lower KGI_ROUTE_AUTO_APPROVE in .env for bulk/benchmark runs; fix the resolution signal to reward decisive no-matches (≈0.9 for "confidently new"); calibrate thresholds against the gold labels in examples/benchmarks/ once the eval harness exists (Scaling up).

08 · Query path & RRF

Reciprocal Rank Fusion — the entire implementation

The three doors return scores that cannot be compared: a cosine similarity of 0.8 and a Lucene BM25 score of 7.3 live on different scales. RRF[11] throws the scores away and keeps only positions: each candidate entity earns 1/(60+rank) per list it appears in, summed. Appearing in two doors beats topping one. The constant 60 is straight from the 2009 paper.

CODEsrc/kgi/retrieval/search.py · _rrf_seeds() — this is all of it
def _rrf_seeds(ranked_lists, k=60):
    scores = {}
    for lst in ranked_lists:              # four lists: the fact doors contribute
        seen, rank = set(), 0             #   the ENDPOINTS of matching facts
        for nid in lst:
            if nid in seen: continue
            seen.add(nid); rank += 1
            scores[nid] = scores.get(nid, 0.0) + 1.0 / (k + rank)
    return [nid for nid, _ in sorted(scores.items(), key=lambda x: -x[1])]

seeds = _rrf_seeds([entity_vector_hits,        # door 1
                    fact_vector_endpoints,     # door 2 -> subject_id, object_id
                    lexical_entity_hits,       # door 3a
                    lexical_fact_endpoints])   # door 3b
        [:10]                                  # MAX_SEEDS — the walk starts here

Ingestion throughput

  • Parallel extraction. Step 3 is one LLM call per paragraph, currently sequential — LangGraph's fan-out (Send()) makes a 50-paragraph document ~10× faster for the same cost.
  • A work queue in front of the pipeline. Two simultaneous ingests can both decide "Acme is new" and create twins. Serialize per scope: a Postgres queue (SELECT … FOR UPDATE SKIP LOCKED) at today's scale; Kafka partitioned by tenant when volume, replay, or multiple producers justify the ops cost.
  • The queue can't fix everything: runs pause at review for days, so strict ordering is impossible by design. The complement is a commit-time check — a name-uniqueness assumption on every create_node op, so the second twin re-queues into dedup instead of being created. Queue for throughput, assumptions for correctness.

Multi-tenant

  • Pooled (one graph, tenant_id on everything) is feasible because all store access already goes through a few chokepoint classes — but nothing in Neo4j Community enforces the filter; one missed WHERE is a breach. The silent killer: entity dedup across tenants — client A's "Acme" must never merge with client B's. Every lookup, vector search, and vocabulary prompt needs the scope; document hashes become (tenant, hash) pairs.
  • Database-per-tenant (Neo4j multi-database or separate containers) is the answer for anyone who asks "what enforces isolation?" — connections are already centralized, so the code change is small. Offer pooled as the cheap tier, siloed as the compliance tier.

Data volume

  • Query-side caps: the viewer returns the whole graph and retrieval walks whole neighborhoods — both need pagination and hub-node limits around ~10⁴ nodes (generic nodes like "Investment Banking" become bridges that pull in half the graph).
  • Corpus-level questions ("what are the main themes?") need the community-summary layer from GraphRAG[1] — the one capability that design deliberately left to steal later, over our governed facts instead of raw extraction.
  • Ops maturity travels with size: backups (Neo4j Community has no hot backup), test isolation (the suite currently wipes the dev database), remediation tooling (forced re-ingest, quarantine flags), and a real eval harness gating prompt/model changes.

Publications and systems informing the design

  1. Edge et al., "From Local to Global: A GraphRAG Approach" (2024) — LLM-built graphs as retrieval substrate; local/global search framing. Adopted: local search. Deferred: community summaries.
  2. Lairgi et al., "iText2KG: Incremental Knowledge Graphs Construction" (WISE 2024, arXiv:2409.03284) — incremental construction, embedding-cosine entity resolution. Adopted as cascade tier 2, with thresholds recalibrated on measured collision pairs (aliases ≈0.99 vs distinct siblings ≈0.87).
  3. Rasmussen et al., "Zep: Graphiti" (2025) — bi-temporal knowledge-graph memory: validity windows instead of deletion. Adopted for all facts; basis of as-of queries.
  4. "ATOM: Atomic-fact decomposition" (arXiv:2510.22590) — proposition-level units for extraction precision. Designed upgrade path behind the decomposition seam.
  5. Bai et al., "AutoSchemaKG" (arXiv:2505.23628) — dynamic schema induction. Adopted with governance added: induced types are human-gated under a thin upper ontology.
  6. SCICERO / HITL-validation line (ScienceDirect, 2025) — source-support counts as confidence signal; human validation loops. Adopted in the scorer and the gate design.
  7. "Less is More: Denoising Knowledge Graphs for RAG" (arXiv:2510.14271) — entity resolution as retrieval quality control. Justifies the LLM judge tier and the conservative no-merge default.
  8. Guo et al., "LightRAG" (2024) and "LLM-empowered KG construction: a survey" (arXiv:2510.20345) — design-space and cost-tier mapping used in the layer-by-layer option analysis.
  9. Neo4j LLM Knowledge Graph Builder — reference implementation of extraction→Neo4j plumbing; baseline the staging/commit split improves on.
  10. Chen et al., "Dense X Retrieval: What Retrieval Granularity Should We Use?" (EMNLP 2024) — propositions (atomic facts) outperform passages as the retrieval unit. Adopted as the fact-vector door: one point per committed edge, embedding its rendering, window, and quotes.
  11. Cormack, Clarke & Büttcher, "Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods" (SIGIR 2009) — rank-based fusion of incomparable scoring systems. Adopted verbatim (k=60) to fuse the retrieval doors into walk seeds.

The combination not found in any single source: extraction reviewed like a pull request — staged patches, a human approval step, rebase-style checks at commit, and audit records written in the same transaction as each fact.
